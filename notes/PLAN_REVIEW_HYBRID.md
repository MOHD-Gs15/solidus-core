# مراجعة هندسية — خطة "Hybrid (A→B)" المقترحة: PostgreSQL + Redis

> التاريخ: 2026-09-06 | يقارن: 2.2.0 الفعلي على origin/main | المنهجية:
> كل ادعاء في الخطة المقترحة قورن بالكود الحقيقي سطراً سطراً قبل الحكم عليه.
> لا شيء في هذا الملف مُخترع؛ كل الادعاءات المرجعية تحمل مواضعها في الكود.

---

## 1. الحكم الإجمالي

الاتجاه الكبير في الخطة المقترحة **سليم ومطابق لجوهر خطتنا الحالية**
(`docs/DB_SCALING_PLAN.md`): سلطة مالية واحدة مشتركة (قاعدة بيانات مركزية
بمعاملات ACID)، وRedis طبقة تنسيق فقط وليس مصدر حقيقة، وأقفال صفوف بدل
"الـ executor هو القفل". هذه ليست مصادفة — هي نفس الخلاصة التي انتهت إليها
خطتنا، وكل إجماع هندسي في الأنظمة المالية.

لكن الخطة المقترحة كُتبت **دون قراءة هذا الكود**، وفيها:

- **مرحلة كاملة (المرحلة 1: إزالة الحظر) مبنية على ادعاء غير صحيح** —
  الحظر غير موجود أصلاً في الكود الإنتاجي.
- **ثلاثة أخطاء كود حقيقية** في الأمثلة المرفقة بالخطة، لو نُفذت حرفياً
  لإسقطت النظام (تفاصيل §3).
- **اختيار قاعدة بيانات لا يطابق طلب المجتمع** ولا واقع استضافة
  ماينكرافت (تفاصيل §4.1).
- **مبالغة في النطاق** لمشروع مود بمُتابع واحد (تفاصيل §4.3).

والخطة تضيف أيضاً **قيمة حقيقية** تستحق التبني في خطتنا (§5).

## 2. الفرضيات الخاطئة عن الكود الحالي (مثبتة بالأسطر)

### 2.1 "ShopManager.buyItem يستخدم .join() — يجب مرحلة كاملة لإزالة الحظر"

**غير صحيح.** فحص `grep` على كامل `src/main/java` لـ `.join()`, `.get()`,
`Thread.sleep` يرجع **صفر نتائج كود** — الكلمة الوحيدة الموجودة هي في
التعليقات التي توثق أن الكود *يتجنبها عمداً*:

- `auction/AuctionManager.java:52` — "instead of .join(). This ensures the
  server tick thread is never blocked"
- `auction/AuctionManager.java:505` — "The entire purchase flow uses
  CompletableFuture chaining instead of .join()"
- `shop/ShopManager.java:443` — "No .join() is used - the balance add
  operation is chained with"

كل مسارات المال تعمل بالسلاسل غير الحاجبة على executor أحادي الخيط منذ
2.1.x. **"المرحلة 1" في الخطة المقترحة منجزة فعلياً، ومعيار الخروج الخاص بها
(`grep` = صفر) محقق اليوم.** هذا يوفر 1–2 أسبوع من التقدير المعلن.

### 2.2 "أزل كل double من الواجهة (BigDecimal في كل مكان)"

**نصف الحقيقة.** المطلوب هو إزالة `double` من *حدود التخزين*، لا من *كامل
الواجهة*. الأدلة:

- سطح API العام كله `double`: `api/SolidusAPI.java` — `getBalance()` يرجع
  `CompletableFuture<Double>`، `addBalance(player, double)` ... إلخ
  (أسطر 115–175). أطراف خارجية تتكامل عبر `EconomyHooks`/
  `SolidusTransactionHook` على نفس الأنواع.
- **309 اختبارات** مبنية على هذا السطح.
- الحماية من الانحراف العشري موجودة أصلاً كنقطة اختناق واحدة:
  `util/CurrencyUtil.java:134+` (`round` إلى منزلتين)، بحدود صريحة
  `MIN_TRANSACTION=0.01`, `MAX_TRANSACTION=10M`, `MAX_BALANCE=100M`
  (أسطر 69–75).

إجبار `BigDecimal` على الواجهة العامة = كسر توافق المصدر مع كل مستهلك خارجي
ولأختباراتنا — ترقية كبرى بمعنى `VERSIONING.md`، مقابل كلفة لا تضيف سلامة
مالية طالما أن:

1. الأعمدة في القاعدة الجديدة `DECIMAL(18,2)` (لا `REAL`)، و
2. التحويل double↔BigDecimal يحدث في **غلاف Money واحد عند حدود التخزين**
   (وهذا بالضبط ما تنص عليه خطتنا §5.4).

الخطة المقترحة صحيحة في *النتيجة* (لا حساب مالي خام فوق float عبر الشبكة)
وخاطئة في *موضع التدخل*.

### 2.3 تقديرات المدة

مرحلتا 0+1 في الخطة (2–4 أسابيع) هما في واقع هذا الكود: استخراج واجهة
`StorageBackend` فقط (سطح البرمجيات الأساسية موجود وموحّد أصلاً —
`transferAtomic(WithLedger)`, `subtractBalance`, `addBalance`, `setBalance`,
`hasBalance`, `getTopBalances`, `getEconomyStats`). التقدير الواقعي: ~أسبوع.

## 3. أخطاء تقنية في أمثلة كود الخطة المقترحة

هذه ليست "اختلاف رأي" — أخطاء تُسقط النظام لو نُفذت حرفياً:

### 3.1 Trigger توازن الـ ledger يفشل عند أول ساق

الخطة تعرف الـ trigger هكذا:

```sql
CREATE TRIGGER ledger_balance_check AFTER INSERT ON ledger_entries
FOR EACH ROW EXECUTE FUNCTION check_ledger_balance();
```

`FOR EACH ROW` يعني أن الفحص يُطلق **عند إدخال ساق DEBIT وحدها** — في تلك
اللحظة Σdebit = المبلغ وΣcredit = 0 → `RAISE EXCEPTION` → **كل تحويل مالي
يفشل دائماً**، والمعاملة تتراجع عند أول إدخال.

**التصحيح** — قيد مؤجل يُفحص عند COMMIT عندما يكون كلا الساقين موجودين:

```sql
CREATE CONSTRAINT TRIGGER ledger_balance_check
AFTER INSERT ON ledger_entries
DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION check_ledger_balance();
```

### 3.2 مفتاح التشغيل الواحد يرمي استثناءً بدل إرجاع النتيجة

```sql
INSERT INTO operations (op_id, ...) VALUES (?, ?, 'TRANSFER', NULL)
RETURNING result_state
```

إذا وُجد `op_id` مسبقاً (وهذا هو **حالة الإعادة** التي صُمم الجدول من أجلها!)
فإن INSERT العادي يرمي `unique_violation` ولا يرجع الصف الموجود. الكود
المقترح يتعامل مع "الصف موجود" لكنه لن يصل إليه أبداً — سيقع في catch.

**التصحيح** — حيلة insert-or-get المعيارية:

```sql
INSERT INTO operations (op_id, account_uuid, op_type, result_state)
VALUES (?, ?, 'TRANSFER', NULL)
ON CONFLICT (op_id) DO UPDATE SET op_type = EXCLUDED.op_type
RETURNING result_state;
-- إذا رجع result_state غير NULL → العملية منفذة سابقاً: أرجع النتيجة المخزنة
```

### 3.3 NOTIFY لا يقبل معاملات ربط

```java
conn.prepareStatement("NOTIFY balance_update, ?")  // غير صالح
```

`NOTIFY` لا يقبل bind parameters أصلاً، وصيغة `NOTIFY channel, payload`
بمتغير مرتبط غير صحيحة نحوياً. **التصحيح**: `SELECT pg_notify(?, ?)` مع
اتصال LISTEN مخصص منفصل (الخطة ذكرت الاتصال المخصص لاحقاً — لكن كود الإرسال
المقترح لن يُجمّع/لن يعمل).

### 3.4 Executor بقائمة انتظار غير محدودة

`Executors.newFixedThreadPool(4)` = قائمة انتظار **غير محدودة**. عند انقطاع
DB لمدة دقائق: كل طلبات الشراء/التحويل تتراكم بلا حد (تضخم ذاكرة)، وعند
التعافي تُنفذ دفعة طلبات قديمة ربما تخلى أصحابها عنها. **التصحيح**:
`ThreadPoolExecutor` بحد أقصى للقائمة + سياسة رفض تترجم لرسالة "النظام مشغول
— حاول مجدداً". (معالجات failed futures موجودة أصلاً في كل الاستدعاءات —
ميزة قائمة في الكود يجب البناء عليها.)

### 3.5 ملاحظة منطقية: "لاعب واحد على سيرفر واحد ⇒ لا تزامن"

الاستنتاج غير دقيق حتى لو كانت الروح صحيحة: التزامن الحقيقي ليس على مستوى
"العملية" بل على مستوى **الحساب والمورد**: لاعب ينتقل بين سيرفرين أثناء
عملية قائمة، ومزايد اثنان على سيرفرين مختلفين لنفس الإعلان، ومسّاح انتهاء
يعمل على كل سيرفر. الخطة نفسها تعترف بهذا ضمنياً بقسم SKIP LOCKED. الحماية
تأتي من قاعدة البيانات (أقفال صفوف + تحديثات شرطية) — كما في خطتنا — لا من
"وحدة المنفذ".

## 4. قرارات تحتاج إعادة موازنة

### 4.1 PostgreSQL مقابل طلب المجتمع (MySQL/MariaDB)

الطلب المجتمعي الأصلي الذي أسّس هذه المهمة نصّ حرفياً على غياب
**MySQL/MariaDB/Redis**. واستضافة ماينكرافت (لوحات Pterodactyl، الاستضافات
المشتركة) تقدم MariaDB شبه دائماً وPostgreSQL نادراً.

والأهم تقنياً: **التصميم المقترح لا يحتاج فعلياً ميزات Postgres الحصرية** —
الطبقة التي كانت ستستفيد من `LISTEN/NOTIFY` (إبطال الكاش) موجودة أصلاً في
التصميم عبر Redis Pub/Sub. و`SKIP LOCKED` مدعوم في MySQL 8+ وMariaDB 10.6+.

- **التوصية**: MariaDB هدف أساسي (كما في خطتنا) — يطابق طلب المجتمع وواقع
  الاستضافة. تبقى واجهة `StorageBackend` تفتح باب `PostgresStorage`
  لاحقاً إذا قررت الشبكة الاستضافة الذاتية بDocker (حينها تنطبق ميزات
  Postgres الإضافية).
- إذا اختلف صاحب المشروع وفضّل Postgres من اليوم الأول: مقبول هندسياً،
  بشرط توثيقه كمتطلب نشر صريح (self-hosted).

### 4.2 القيد المزدوج الكامل + triggers — قيمة عالية، لكن ليس الآن ولا بهذه الكلفة

منع الازدواج لا يحتاج قيداً مزدوجاً — يأتي من معاملات القاعدة والأقفال
والتحديثات الشرطية (الموجودة أصلاً: `UPDATE ... WHERE status=0` claims،
`BEGIN IMMEDIATE`). القيمة الحقيقية للقيد المزدوج هي **التدقيق وتعقّب
السكّ** (mint visibility). بديل أدنى كلفة يعطي 90% من الفائدة:

1. الإبقاء على الـ ledger الحالي (صف واحد لكل حدث، يُدخل داخل معاملة المال —
   هذه الخاصية "money ↔ evidence" هي الجوهر وهي محفوظة).
2. إضافة جدول `operations` (مفاتيح تشغيل واحد) — §5.1 أدناه.
3. **مهمة تسوية دورية**: `SUM(ledger per account)` مقابل `balance` مخزّن،
   وتنبيه عند انحراف > 0.01 — تكشف أي خلل (سك أو فقد) بلا triggers ولا
   إعادة تصميم.

الترقية الكاملة لقيد مزدوج تبقى خياراً موثقاً لاحقاً (بtrigger مؤجل مصحح
§3.1) إن نضجت متطلبات التدقيق.

### 4.3 نطاق مبالغ فيه للحالة الفعلية

Presence map، الأقفال الموزعة، Outbox، Grafana/Prometheus، WAL archiving —
كلها أدوات صحيحة، لكنها طبقات لا تلمس سلامة المال، وترتيبها الصحيح:

- **الآن (يمنع الازدواج)**: DB مشتركة + معاملات + أقفال صفوف بترتيب UUID
  + تحديثات شرطية + DECIMAL.
- **بعدها (سرعة ووعي شبكي)**: Redis كاش + pub/sub إشعارات (اختياري —
  شبكة MySQL-only تعمل كاملاً بدونه، كما في خطتنا §6).
- **لاحقاً حسب الحاجة المقاسة**: Outbox (أو مجرد مسّاح polling بسيط على
  الجداول المشتركة — أسهل وأكفي كبداية)، Presence، مراقبة Prometheus،
  PostgresStorage.

### 4.4 شرط صامت مُهمَل: حجم الجار والتغليف

مود Fabric يغلّف تبعاته (`include` في build.gradle). إضافة HikariCP +
mariadb-driver + lettuce تعني جار أكبر و_surface** تبعات أعلى — يجب حسابه
وتوثيقه (وكذلك بقاء sqlite-jdbc مضمّناً كوضع افتراضي). الخطة المقترحة تفترض
بنية تحتية جاهزة ولا تذكر الكلفة على التوزيع.

## 5. ما تستحق الخطة المقترحة التبنيه فعلاً (إضافات موثقة لخطتنا)

1. **جدول `operations` (idempotency keys)** — رخيص وعالي القيمة على شبكة:
   نفس العملية المعاد إرسالها (شبكة متقطعة، إعادة محاولة من اللاعب) ترجع
   نفس النتيجة بلا خصم مزدوج. يضاف لمرحلة MySQL (2.4.0) بالصيغة المصححة §3.2.
2. **حماية overflow في SQL نفسه** بدل فحص Java فقط:
   `UPDATE ... SET balance = balance + ? WHERE balance + ? <= MAX_BALANCE`
   — على شبكة، السيرفران قد يراهما صالحين في Java ثم يتسابقان؛ الفحص داخل
   معاملة القاعدة هو الحكم. (الحدود موجودة أصلاً: `CurrencyUtil.MAX_BALANCE`
   = 100M — تُثبّت كثابت SQL مطابق).
3. **SKIP LOCKED لمسّاحات انتهاء المزادات** — مدعوم MariaDB 10.6+/MySQL 8+؛
   يجعل مسح انتهاء الإعلانات آمناً ومنظماً عند تعدد السيرفرات (خطتنا كانت
   تعتمد على row guards وحدها — SKIP LOCKED يقلل التنافس أيضاً).
4. **سيناريوهات اختبار الشبكة السبعة** (نقل عابر للسيرفرات، محاولة ازدواج
   < 100ms، إعادة إرسال بنفس المفتاح، قطع اتصال أثناء معاملة، مسح متزامن،
   TPS تحت تحميل، استرداد من كوارث) — قائمة ممتازة، تُتبنى حرفياً في
   harness الشبكة (مرحلة 2 لدينا).
5. **فصل writePool/readPool** كتصميم مستقبلي (مع replica لاحقاً) — ليس
   ضرورياً في v1، لكنه قرار واجهة صحيح يُوثق الآن ليُبنى عليه.

## 6. ما تنقصه الخطة (ثغرات تشغيلية يجب ألا تُنسى)

1. **إصدارات schema**: جدول `schema_version` + تحققات بدء تشغيل (خطتنا §9
   تغطيها؛ Flyway ثقيل لمود — نسخة مبسطة تكفي).
2. **مهمة تسوية** روتينية (§4.2 أعلاه) — أرخص خط دفاع بعد الـ ledger.
3. **Housekeeping**: تنظيف `operations`/outbox الأقدم من 30 يوماً؛ تخطيط
   تقسيم ledger مستقبلاً (append-only ينمو للأبد).
4. **وضع التدهور عند انقطاع DB**: read-only عبر config أو fail-closed،
   مع circuit breaker — الأرصدة لا تظهر صفراً أبداً (خطتنا §9).
5. **SQLite يبقى الافتراضي للسيرفر المفرد** — الشبكة تختار MySQL عبر
   config. الخطة المقترحة تفترض Postgres+Redis للجميع: overkill للحالة
   الغالبة (سيرفر مفرد) ويرفع كلفة الدخول بلا مقابل.
6. **بنية الاختبار**: الحالية JUnit 5 + Mockito (309 اختبار) بلا
   Testcontainers — إضافته (MariaDB container للـ contract tests) خطوة
   صريحة مطلوبة قبل harness الشبكة، لا افتراض جاهز.

## 7. خارطة الطريق المدموجة (الخلاصة التنفيذية)

| الإصدار | المحتوى | مصدر العناصر |
| --- | --- | --- |
| **2.3.0** | واجهة `StorageBackend` + غلاف `Money` حدودي + فصل dialect hooks — refactor نقي، الـ 309 اختبار تبقى خضراء | خطتنا مرحلة 1 (الخطة المقترحة لا تضيف شيئاً هنا — "مرحلة الحظر" عندها منجزة أصلاً) |
| **2.4.0** | `MySqlStorage` (Hikari، `DECIMAL(18,2)`، `FOR UPDATE` بترتيب UUID، `ON DUPLICATE KEY`، جدول `operations` بالمفاتيح، حماية overflow داخل SQL، `SKIP LOCKED` sweeps، أمر ترحيل عابد الإعادة) + Testcontainers + harness السيناريوهات السبعة | خطتنا مرحلة 2 + إضافات الخطة §5.1–5.4 |
| **2.5.0** | Redis اختياري (L1/L2 + pub/sub إشعارات وأحداث) + توصيل إشعارات عابر للشبكة + job تسوية دوري | خطتنا مراحل 3–4 |
| **لاحق** | Outbox، Presence، `PostgresStorage`، قيد مزدوج كامل (بtrigger مؤجل مصحح)، Prometheus | إضافات الخطة المقترحة المؤجلة بحسب الحاجة المقاسة |

**الخلاصة**: الخطة المقترحة استشارية حسنة المبادئ لكنها كُتبت دون قراءة هذا
الكود — تُحمّلنا مرحلة منجزة أصلاً، وتحمل 3 أخطاء كود ستُسقط النظام لو نُفذت
حرفياً، وتختار قاعدة بيانات لا يطلبها المجتمع ولا يفرضها التصميم. الدمج في §7
يلتقط كل قيمتها الحقيقية (idempotency، overflow guard في SQL، SKIP LOCKED،
سيناريوهات الاختبار) دون تكاليفها.
